# План работ — LAN Desktop Stream

## 1. Цель проекта

Разработать приложение для трансляции рабочего стола по локальной сети с минимальной нагрузкой на ПК-источник, высоким качеством изображения и минимальной задержкой.

### Архитектура

- На ПК-источнике устанавливается небольшая Windows-программа.
- Пользовательские ПК ничего не устанавливают: просмотр выполняется через браузер.
- Центральный сервер предоставляет WebRTC-сигнализацию и управление трансляциями.
- Основной протокол передачи медиаданных — WebRTC/RTP по UDP.
- Основной видеокодек — H.264.
- Предусмотреть возможность подключения нескольких пользователей.
- Пользователь должен иметь возможность одновременно смотреть несколько трансляций в одном окне браузера.

## 2. Технологический стек

### ПК-источник

- Язык: **Python**.
- WebRTC: **aiortc**.
- HTTP/WebSocket: **aiohttp**.
- Захват экрана: **mss** на первом этапе.
- Обработка/кодирование: PyAV/OpenCV там, где необходимо.
- Приоритет — минимизация копирования кадров и использование аппаратного H.264, если это возможно в выбранной реализации.

### Сервер

- WebRTC-сигнализация.
- Управление источниками и пользователями.
- Реестр доступных трансляций.
- SFU/маршрутизация медиапотоков — архитектуру подготовить так, чтобы поток источника не перекодировался для каждого пользователя.

### Браузерный клиент

- HTML5 + JavaScript/TypeScript.
- WebRTC API.
- `<video>` для отображения потоков.
- Полноэкранный режим.
- Сетка нескольких трансляций.

## 3. Логика подключения

### Источник

1. Запускается приложение на ПК-источнике.
2. Пользователь задаёт источник изображения: монитор или окно.
3. Задаются разрешение, FPS, битрейт и название трансляции.
4. Источник подключается к серверу и регистрирует трансляцию.
5. Сервер отображает источник как доступный.

### Пользователь

1. Пользователь открывает в браузере адрес сервера по IP и порту.
2. Сервер показывает список доступных трансляций.
3. Пользователь выбирает одну или несколько трансляций.
4. Для каждой выбранной трансляции устанавливается WebRTC-подключение/медиа-трек через сервер.
5. Пользователь может открыть прямую ссылку на конкретную трансляцию.

IP самого ПК-источника пользователю вводить не требуется.

## 4. Захват и передача изображения

### 4.1 Захват

- Реализовать захват выбранного монитора.
- Реализовать захват отдельного окна.
- Минимизировать преобразования и копирование кадров.
- Контролировать реальный FPS захвата.

### 4.2 Кодирование

- Основной формат: H.264.
- Приоритет: аппаратное кодирование.
- Предусмотреть определение доступного аппаратного encoder.
- Для NVIDIA — NVENC.
- Для Intel — Quick Sync.
- Для AMD — AMF.
- Предусмотреть программный fallback, если аппаратный encoder недоступен.
- Настройки кодирования ориентировать на screen content и низкую задержку.

### 4.3 WebRTC

- Реализовать SDP offer/answer.
- Реализовать ICE candidate exchange.
- WebSocket использовать для signaling.
- RTP/RTCP использовать через WebRTC.
- Основной транспорт медиаданных — UDP.
- Корректно обрабатывать переподключение и отключение клиента.

## 5. Сервер и управление потоками

### 5.1 Реестр источников

Для каждого источника хранить:

- уникальный ID;
- название;
- IP/сетевые сведения, необходимые серверу;
- статус Online/Offline;
- разрешение;
- FPS;
- текущий bitrate.

### 5.2 Пользователи

- Отображать подключённых пользователей.
- Отслеживать активные подключения.
- Корректно удалять отключившихся пользователей.
- Не создавать нового пользователя при обычном переподключении существующего клиента.
- Предусмотреть принудительное отключение пользователя.

### 5.3 SFU / оптимизация раздачи

- Источник должен кодировать один видеопоток, а не выполнять отдельное кодирование для каждого пользователя.
- Сервер должен раздавать уже закодированный поток клиентам.
- Архитектура должна поддерживать несколько источников одновременно.
- Архитектура должна поддерживать несколько пользователей на одном источнике.

## 6. Браузерный клиент

### 6.1 Основной интерфейс

- Список доступных трансляций.
- Подключение/отключение трансляции.
- Кнопка копирования ссылки.
- Полноэкранный режим.
- Отображение названия источника.
- Индикация состояния соединения.

### 6.2 Несколько трансляций

- Одно окно браузера должно поддерживать несколько одновременно отображаемых потоков.
- Режимы сетки: 1 / 2 / 4 / 9 / 16 потоков.
- Возможность сделать выбранную трансляцию полноэкранной.
- Возможность менять порядок потоков.
- Отключение отдельных потоков без закрытия страницы.

## 7. Адаптация качества и сети

- Автоматически отслеживать состояние соединения.
- Реализовать адаптивный bitrate.
- При ухудшении сети уменьшать bitrate.
- После восстановления сети возвращаться к выбранному пользователем значению.
- Не допускать бесконтрольного роста bitrate.
- Приоритет — сохранение плавности и минимальной задержки.

## 10. Производительность

Главный критерий оптимизации — минимальная нагрузка на ПК-источник.

Проверять:

- CPU при 720p/30;
- CPU при 1080p/30;
- CPU при 1080p/60;
- влияние количества пользователей;
- влияние разрешения;
- влияние bitrate;
- влияние захвата окна вместо монитора;
- поведение при отсутствии аппаратного encoder.

Целевой ориентир по задержке: **менее 200 мс в нормальной локальной сети**.

## 15. Критерии готовности

Проект считается готовым, если:

- ПК-источник запускает приложение без необходимости устанавливать Python.
- Рабочий стол транслируется в браузер.
- Используется WebRTC.
- Используется H.264.
- Передача работает по LAN.
- Задержка в нормальной LAN укладывается в целевой показатель <200 мс.
- Несколько пользователей могут одновременно смотреть один источник.
- Один браузер может одновременно отображать несколько источников.
- Переподключение не создаёт бесконечные новые сессии.
- Есть диагностика и логи.
- Есть автоматическая настройка Firewall.
- Windows-сборка готова к использованию конечным пользователем.
